# ADR 0008 — NDI® : plugin GStreamer compilé dans le binaire, runtime chargé dynamiquement

- **Statut** : **proposé** (2026-11-02), à valider
- **Date** : 2026-11-02
- **Contexte** : BRIEF §2.6 (SDK NDI propriétaire : chargé dynamiquement, jamais embarqué,
  conditions de marque respectées), §4 (Phase 3 : NDI en entrée et en sortie, désactivé
  proprement si absent), §6 (`ndisrc` / `ndisink` de `gst-plugins-rs`) ; ADR 0004, ADR 0006 ;
  spec [`docs/specs/phase-3.md`](../specs/phase-3.md)

NDI® est une marque déposée de Vizrt NDI AB.

## Faits vérifiés (documentation publique, 2026-11-02)
- Le plugin `ndi` de `gst-plugins-rs` (crate **`gst-plugin-ndi`** 0.15.4, **MPL-2.0**,
  `gstreamer` 0.25 / `glib` 0.22 comme le reste du projet, Rust ≥ 1.92) fournit `ndisrc`,
  `ndisrcdemux`, `ndisink`, `ndisinkcombiner` et un fournisseur de périphériques (découverte des
  sources). Il **ne se lie pas au SDK** : il charge la bibliothèque NDI à l'exécution
  (`libloading`), depuis le chemin par défaut ou le dossier de `NDI_RUNTIME_DIR_V6` /
  `NDI_RUNTIME_DIR_V5` ; compatible SDK 5 et 6.
- Le plugin n'est empaqueté ni dans les dépôts officiels d'Arch (AUR seulement,
  `gst-plugin-ndi-git`), ni de façon certaine dans l'installeur GStreamer Windows.
- La documentation du SDK NDI : utilisation gratuite ; bibliothèques redistribuables sous
  conditions (licence reprise dans l'application) ; le nom « NDI » porte le ® à sa première
  occurrence avec la mention « NDI® is a registered trademark of Vizrt NDI AB », reprise aussi
  dans la fenêtre « À propos » ou équivalent ; les règles de marque (*brand guidelines*) sont
  à lire avant de nommer un produit avec « NDI ».

## Décision
1. **`gst-plugin-ndi` est une dépendance Cargo de `io-ndi`**, enregistrée comme plugin statique
   au démarrage de `vma-io` (`gstndi::plugin_register_static()`). Le plugin est donc présent sur
   les deux OS sans paquet à installer ; seul le **runtime NDI** (fourni par l'utilisateur :
   « NDI Tools » / runtime officiel, ou `ndi-sdk` d'AUR) reste externe.
2. **Le runtime n'est jamais embarqué ni redistribué** par VMA : ni dans le dépôt, ni dans les
   binaires, ni dans un installeur. Pas de recherche dans des chemins exotiques : chemin par
   défaut et variables `NDI_RUNTIME_DIR_V6` / `_V5` (celles du plugin).
3. **Détection au démarrage** (`io-ndi`) : on tente de créer un `ndisrc` (qui charge le runtime)
   ; état publié `IoStatus::ndi = Available { version } | Unavailable { reason }`. Absent : les
   inputs et sorties NDI sont **refusés avec leur raison**, l'UI grise les boutons NDI et dit
   comment installer le runtime ; rien d'autre ne change. Pas de nouvelle tentative pendant
   l'exécution (redémarrer VMA après installation).
4. **Marque** : « NDI® » à la première occurrence de chaque écran qui en parle (fenêtre
   d'ajout d'input, fenêtre Sorties), mention « NDI® is a registered trademark of Vizrt NDI
   AB » dans une nouvelle fenêtre « À propos » (licences des dépendances, dont MPL-2.0 de
   `gst-plugin-ndi`) et dans le `README`. Aucun logo NDI. VMA ne se nomme pas avec « NDI ».
5. **Licence** : MPL-2.0 ajoutée à la liste `cargo deny` **pour cette seule crate**
   (exception, comme les polices d'egui) : copyleft limité aux fichiers du plugin, compatible
   MIT / Apache-2.0 pour le reste ; le code source du plugin reste celui de crates.io (aucune
   modification de notre part). `libloading` : ISC. `quick-xml`, `data-encoding`,
   `byte-slice-cast`, `smallvec`, `byteorder` : MIT / Apache-2.0 (à confirmer par `cargo deny`).
6. **CI** : pas de runtime NDI (téléchargement soumis à l'acceptation de sa licence, Q4) :
   la CI teste le chemin « runtime absent » sur les 2 OS (refus propres, UI) ; les tests NDI
   réels (boucle locale `ndisink` → `ndisrc`, synchro flash / bip) sont **conditionnels**
   (`VMA_REQUIRE_NDI`, comme `VMA_MEDIAMTX`) et passés sur la machine de dev.

## Entrée et sortie (détail dans la spec)
- **Entrée** : `ndisrc ! ndisrcdemux` → branches vidéo (UYVY, I420, NV12, BGRA… vers l'upload
  existant) et audio (ADR 0007) ; horodatage par l'horloge du pipeline (mode de `ndisrc`
  choisi pour donner des temps de flux dans le domaine maître, à vérifier à l'étape 7) ; source
  disparue → signal perdu, reconnexion par nom (politique 1 / 2 / 5 / 10 s).
- **Sortie** : `appsrc` (NV12 de l'étage de sortie, ADR 0006) + `appsrc` audio (bus de la
  sortie) → `ndisinkcombiner` → `ndisink`, sans encodage ; nom annoncé réglable (défaut
  « VMA Program »). Une sortie NDI au plus en Phase 3.

## Alternatives examinées
- **Nos propres bindings** (`libloading` + FFI du SDK dans `io-ndi`) : contrôle total, mais du
  code `unsafe`, un format d'en-têtes à suivre, et tout ce que le plugin fait déjà (découverte,
  conversions, horodatage). Écarté ; reste possible derrière le même `io-ndi` si le plugin
  bloque un besoin.
- **Exiger le plugin installé par le système** (pas de dépendance Cargo) : simple, mais
  indisponible sous Arch hors AUR et incertain sous Windows ; la fonctionnalité serait absente
  pour la plupart des utilisateurs même avec le runtime. Écarté.
